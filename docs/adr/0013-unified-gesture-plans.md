# ADR 0013: Unified Gesture Plans

## Status

Accepted

Completed process history is in git history.

## Rules at a glance

- Normalize public gesture input once in `packages/contracts/src/gesture-normalization.ts`.
- Plan canonical intent in `packages/contracts/src/gesture-plan.ts`. Keep contact topology separate from motion.
- Reject removed timed public forms with actionable `INVALID_ARGS` messages.
- Keep Maestro's `endpoint-hold` profile private. Public `pan` uses `timed-pan`.
- Every injected sample must fit the freshly resolved active-app interaction viewport. Never clamp or distort the plan.
- Android touch execution never falls back to `adb input swipe`.
- Keep the positional `.ad` codec and shared `PUBLIC_GESTURE_SYNTAX` arity table.
- Repeated swipe and pause schedules must fit within 60 seconds.
- Before target-authored drag, resolve and verify both endpoints. Admit it only on Android touch devices and iOS/iPadOS.
- iOS timing changes require independent app-observed live simulator evidence.

## Context

Several private boundaries previously interpreted gesture intent:

- Command aliases produced positional strings.
- Daemon dispatch parsed them again.
- `Interactor` exposed parallel semantic methods.
- Each platform derived its own two-contact geometry.

This duplicated validation, responses, and behavior behind CLI, Node.js, and MCP.

Two-contact geometry also differed by platform.
Android used a fixed radius, while Apple derived radius from the app frame.
Neither path validated every planned point against the active interaction viewport before injection.

`scroll` remains separate because it owns viewport/edge traversal and content-state verification, not one physical gesture.
Its Android physical movement still uses the Android planned-touch executor.

## Decision

Public gesture inputs normalize once in `packages/contracts/src/gesture-normalization.ts`.
This is the explicit public compatibility boundary.
It produces canonical semantic intent before runtime entry.
Removed deprecated arguments receive actionable `INVALID_ARGS` errors instead of silent reinterpretation:

- Timed `swipe`.
- Timed `gesture fling`.
- `gesture rotate` `velocity`.

The private daemon wire may still carry compatibility-only hints absent from public surfaces.
Maestro timed swipes use `internal.gestureExecutionProfile: 'endpoint-hold'` with canonical `pan` input.
This preserves iOS fast-swipe-then-hold behavior.

The runtime plans canonical intent in `packages/contracts/src/gesture-plan.ts`.
Contact topology is separate from motion:

- One contact: pan, fling, or target-authored drag with a complete pointer trajectory and explicit execution profile.
- Two contacts: pan, pinch, rotate, or transform with two complete synchronized trajectories.

Public `swipe` without duration remains an alias for fixed-duration fling.
These timed public forms are rejected:

- `swipe x1 y1 x2 y2 durationMs`.
- `gesture fling direction x y distance durationMs`.
- `gesture swipe preset durationMs`.
- `gesture rotate degrees x y velocity`.

For deliberate timed translation, callers must use `gesture pan`.
For rotation, they must use `gesture rotate` without `velocity`.
Maestro swipes normalize to canonical `pan` with origin, delta, and durationMs.
They carry `endpoint-hold` through daemon-internal `internal.gestureExecutionProfile`.
This matches Maestro's XCTest driver without a public execution-profile option.
If duration is absent, Maestro supplies its 400 ms default.
A public `pan` uses `timed-pan`.
Thus, compatibility paths retain release behavior without a new semantic intent.

The plan retains intent even when aliases share an executor:

- Pinch fixes translation and rotation at zero.
- Rotate fixes translation at zero and scale at one.
- Two-finger pan fixes scale at one and rotation at zero.
- Transform can apply all three components atomically.

The planner owns deterministic multi-touch geometry.
Contacts start at -90 degrees, except Android pinch starts horizontally.
Common vertical app scroll containers capture vertical Android pinches before the pinch recognizer activates.
An explicit planning profile also preserves dense two-contact frame-count conventions.
Android rounds the duration/16 ms frame count.
Apple truncates it.
The Android transport lowerer uses the same Android sampling profile for one-contact endpoint plans.
These profiles are planner inputs, not trajectories generated by adapters.

For pinch, the larger initial/final span is 40% of the viewport's shorter side, which preserves proven Apple geometry.
Other two-contact intents use 25% for compact translation and rotation trajectories.
Requested scale determines the other span.
Both spans must satisfy a 48-point reliability floor.
Combined transforms progress translation, scale, and rotation together in one uninterrupted two-contact sequence.
Recognizers observe every intent without adapter-generated geometry.
The planner does not clamp points, cache the viewport, or distort requested components.
Every injected sample must fit the freshly resolved active-app interaction viewport.
Otherwise, the request fails before injection with `GESTURE_TRAJECTORY_OUT_OF_BOUNDS` and actionable details.
Span and angle remain internal because no established automation use case justifies public controls.

Platform adapters consume the canonical plan:

- **Android.** `executeAndroidTouchPlan` receives gesture plans and physical movement for scroll and long-press.
  If provider-native touch injection is available, it uses that provider.
  Otherwise, it uses the bundled instrumentation helper.
  `packages/platform-android/src/touch-plan-lowering.ts` lowers one-contact endpoint plans to approximately 16 ms transport samples before either injection path.
  Controlled directional scrolls accelerate for one frame, then decelerate through release within the requested duration.
  They append no extra movement.
  Inertial scrolls and general one-contact plans retain linear interpolation.
  Two-contact plans retain their exact planned samples.
  Easing reduces release momentum but does not guarantee an exact content offset.
  Transport types require samples strictly denser than the canonical endpoint pair.
  Thus, omitted lowering causes a type error at injection boundaries instead of silently sparse input.
  A stationary long-press needs no viewport on the helper path.
  Only provider-native touch adds the paired provider-owned viewport.
  Android touch execution never falls back to `adb input swipe`.
  Public scroll durations below one 16 ms planner frame normalize to that minimum and report the executed duration.
  Scroll evidence reports absolute injected coordinates against zero-origin extents that include viewport offset.
  Android permits only one instrumentation owner of `UiAutomation`.
  Snapshot capture, gesture viewport resolution, and planned-touch injection therefore share one bundled automation helper.
  A live persistent helper session executes touch commands directly.
  Without one, the same helper runs one-shot.
- **Apple.** iOS lowers one-contact endpoint-hold plans to the established fast-swipe synthesis profile.
  It reaches the endpoint in 100 ms, holds for the planned duration, then lifts, as Maestro's XCTest driver does.
  One-contact plans are linear and carry only start/end samples with the authored duration between them.
  Two-contact plans convert every planned point to native orientation and send the exact arrays to the private XCTest event bridge.
  macOS lowers one-contact plans to its drag executor.
  tvOS lowers them to remote direction.
  Core admission and the Apple adapter consume the same shared multi-touch support policy.
  Multi-touch remains capability-gated to iOS simulators.

  iOS intentionally retains three one-contact motion schedules behind the shared private-XCTest event bridge.
  Apple's public drag API independently models [initial hold, movement velocity, and destination hold](https://developer.apple.com/documentation/xcuiautomation/xcuicoordinate/press%28forduration%3Athendragto%3Awithvelocity%3Athenholdforduration%3A%29).
  UIKit reports finger-up velocity with the predicted [resting content offset](https://developer.apple.com/documentation/uikit/uiscrollviewdelegate/scrollviewwillenddragging%28_%3Awithvelocity%3Atargetcontentoffset%3A%29).
  It then applies the configured [post-lift deceleration rate](https://developer.apple.com/documentation/uikit/uiscrollview/decelerationrate-swift.property).
  Movement distribution over time is therefore observable gesture input, not merely adapter implementation.

  The schedules produce different velocity profiles:

  - `endpoint-hold` moves for 100 ms, then remains stationary before lift.
  - `timed-pan` and target-authored drag submit authored samples unchanged.
    They preserve piecewise-linear movement and explicit source/destination holds.
  - Fused runner `scroll` reuses `endpoint-hold` for inertial release.
    Controlled release expands movement into evenly spaced samples, approximately one per 16 ms, capped at 30.
    It uses cubic ease-out `s(t) = 1 - (1 - t)³`.

  A linear segment retains constant velocity through its endpoint unless a destination hold follows.
  Cubic ease-out decelerates from first movement and has zero slope at lift.
  Its starting velocity is three times its average.
  Thus, identical endpoints and total durations can produce different recognition and deceleration outcomes.
  Neither destination hold nor analytically zero endpoint slope alone proves controlled release.
  XCTest event sampling and app recognizer thresholds can still produce post-lift motion.
  Live evidence must therefore measure content offset after pointer-up.

  Live iOS characterization in [issue #1586](https://github.com/callstack/agent-device/issues/1586) compared an eased sampled schedule with linear schedules.
  In the tested range, they crossed the same fling-recognizer thresholds.
  However, post-release ScrollView positions and long-duration recognition differed materially.
  This distinction is intentional Apple adapter policy, not a second interpretation of `GesturePlan`.
  Changes require live evidence for recognizer activation and post-release content movement.
- **WebDriver.** Supported plans become synchronized W3C pointer action sources.
  One-contact endpoint plans produce pointer down, one timed W3C `pointerMove` from start to end, and pointer up.
  The driver owns interpolation across that W3C tick.
  Multi-touch remains capability-gated until a provider proves it.

`Interactor` and backend expose one compositional `performGesture(plan)` primitive instead of one method per semantic alias.
The old scalar Apple/Android multi-touch executors are deleted.
The public alias-to-positionals-to-reparse route is also deleted.
`.ad` retains its established positional syntax through one named codec.
CLI, Node.js, and MCP send structured input.
Providers should compose transport/device bindings with the shared platform adapter instead of duplicating the interaction runtime.

The `.ad` codec owns script syntax.
It is not a compatibility shim and is not scheduled for removal.
Its callers are CLI argv parse and `.ad` line parse, both current public syntax.
A structured `.ad` gesture payload was rejected because it would reduce readability and text search without behavioral benefit.

One table, `PUBLIC_GESTURE_SYNTAX`, defines argument arity for both callers.
Thus, removal of a CLI form removes the `.ad` form in the same edit.
If a script retains a removed positional, parsing fails before any replay device action.
The error names the offending line and its rewrite.
Only arity is checked at parse time.
`${VAR}` tokens resolve after planning, and interpolation never splits a token.
Thus, counts are known before values.
The public [gesture migration guide](https://oss.callstack.com/agent-device/docs/migrating-gestures) defines this removal process:

1. Announce the removal.
2. Warn for one minor release.
3. Publish the migration guide.
4. Prove that the repository has no remaining use.
5. Remove the branch and its tests.

The public command contract and daemon trust boundary bound repeated coordinate swipes.
Individual count and pause limits prevent pathological fields.
The combined planned gesture and pause schedule must fit within 60 seconds.
Thus, individually valid fields cannot create an unbounded session lock.

Public two-finger pan is additive through `pointerCount?: 1 | 2` and CLI `--pointer-count 2`.
Omission remains one contact.
Responses share canonical `kind`, `durationMs`, `pointerCount`, `from`, and `to`, followed by backend evidence.
Recording/replay retains public command identity and session semantics.

Target-authored drag is additive through `gesture drag <source> <destination>`.
Each endpoint accepts a selector or pinned snapshot ref.
Both endpoints resolve before injection.
Their center points become one uninterrupted single-pointer plan:

1. Hold at the source.
2. Move over the authored duration.
3. If requested, hold at the destination.
4. Release.

The caller receives both endpoint-resolution disclosures and portable selector chains.
Recordings replace both session-local refs with those chains.
One `targets-v1` annotation carries independent source and destination identity evidence.
Before pointer-down, replay verifies both identities.
It guards each independent endpoint resolution against the verified element.
Ref admission occurs for both endpoints before either dispatch.
After the gesture, the usual mutation boundary expires the frame.
Only Android touch devices and iOS/iPadOS admit target-authored drag.
Their adapters preserve the complete source-hold, timed-movement, and destination-hold plan.

ADR 0011's coordinate path remains unchanged.
Coordinate-authored gestures resolve neither selectors nor refs and cannot claim element-targeting guarantees.
Before coordinate gesture execution, target-authored drag runs shared selector/ref preflight.
Tests prove endpoint resolution and recording contracts at that composition boundary.

## Consequences

- CLI, Node.js, MCP, runtime, and adapters share one normalization and planning model.
- A new ergonomic alias does not require a platform implementation.
- One-finger pan remains default, and explicit two-finger pan retains pan intent.
- Each gesture resolves its active viewport.
  Rotation, keyboard, and window changes therefore do not use stale geometry.
- On bare ADB, Android scroll and long-press require the bundled automation helper, the snapshot helper APK, and `UiAutomation`.
  Helper install or runtime failure returns directly instead of approximate `adb input swipe` fallback.
- Canonical one-contact plans contain only two samples.
  A 10-second pan therefore has two shared-plan samples instead of 626.
  Android expands them only at the transport boundary.
  Two-contact plans remain cadence-bounded because synchronized geometry belongs to their contract.
- Unit tests cover plan shape, Android lowering, helper/provider payloads, and WebDriver actions.
  They cannot prove timing or delivery inside the private XCTest bridge.
  iOS timing changes therefore require live simulator evidence from an independent app-observed postcondition.
  Runner start/end uptime deltas can supplement it.
  Request echoes or internal timing alone do not prove recognition of the intended gesture.

## Alternatives Considered

- **Keep positional aliases and share only geometry.** Rejected because validation, response, and routes would retain two implementations.
- **Make platform gesture APIs authoritative.** Rejected because their timing, geometry, and recognition differ and cannot define cross-platform semantics.
- **Make swipe a public synonym for pan.** Rejected because established gesture vocabulary distinguishes quick directional fling/swipe from deliberate timed pan.
- **Add `two-finger-pan`.** Rejected because pointer count defines topology, not new motion intent.
- **Expose span/angle controls.** Rejected until a concrete automation use case requires them.
- **Consolidate scroll semantics.** Rejected because edge/content verification is distinct.
  Only Android physical touch execution is shared.
