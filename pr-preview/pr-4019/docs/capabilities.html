    #Capabilities

    The target tables below are generated from the runtime command-admission facts that back the capabilities command: a command that leaves the code leaves this page. Labels, limits, and integration rows are maintained beside the generator, and command availability does not establish support for every operation, subcommand, or device model. It covers agent-device 0.21.34-dev, generated 2026-10-27.

    Yes means the facts admit every command in that row on the target and every operation the row advertises. No means at least one is refused. A qualified cell names the operations that answer there. Targets that share the same available operations print as one column.

    Physical iOS devices discovered only through xctrace use the XCTest backend rather than CoreDevice: they support open/close, interactions, snapshots, and screenshots, while app inventory, installation, logs, performance sampling, recording, deep links, and launch arguments need CoreDevice.

    One capability depends on the agent machine rather than the target: system audio sampling works only when the daemon runs on macOS, which is what this page assumes.

    Check the device in front of you rather than trusting a table:

    agent-device capabilities --platform ios --device "iPhone 17 Pro"
agent-device capabilities --session my-session --json

    A provider column answers for that provider in its default configuration. Provider credentials, device selection, and artifact retrieval live on the provider pages.

    What a Yes does not claim:

    • Tap, press, fill, and type: Android types non-ASCII text through the test input method: automatically on emulators, and on physical devices only with open --test-ime.
    • Gesture plans and swipes: Multi-touch plans are part of gesture where the target runs them; a plan using an operation the target lacks fails at that step.
    • React Native overlay dismissal: The command runs wherever tapping runs; it answers detected: false on a surface with no React Native overlay. Only iOS and Android apps present dismissable development overlays.

    What a Yes does not claim:

    • Screen recording: An iOS physical device records runner screenshots, not a native video stream: no audio, and dropped frames are expected. An Android clip covers 180 seconds, and a longer recording arrives as chunks.
    • HTTP(S) request inspection: Local native app sessions inspect the HTTP(S) entries present in the session app log; traffic absent from those logs is not captured. The three WebDriver provider clouds refuse a live dump: their traffic is on the provider side, and TestMu AI can return provider network-log artifacts after the session ends. Managed web sessions inspect the browser request history.
    • Audio probe: A simulator, emulator, or macOS desktop session samples host system audio, which works on a macOS agent host and needs Screen Recording permission there.

    What a Yes does not claim:

    • Phone hardware buttons: Each button is a separate operation; a target that answers the row still refuses buttons it does not model.
    • System and app settings helpers: Each helper admits on its own, and a target may run only a subset of the helpers.

    #Capabilities that are not per-device commands

    These come with the tool rather than with a target, so no column above decides them.

    CapabilityWhat it needsWhere it is documented
    React component tree, inspect, and errorsNeeds a React Native or Expo development build that registers the React DevTools backend, reachable through the app Metro dev server. No React DevTools window may be connected.React component tree, inspect, and errors
    React render profilingNeeds a development build of React Native 0.74 or later and its Metro dev server. Verified on Android emulators and iOS simulators, and over proxy and remote bridge sessions.React render profiling
    JavaScript heap and profiles through CDPNeeds a Metro CDP target, so it applies to React Native and Expo apps. It runs a pinned npm helper on the agent host, and the first run may download it.JavaScript heap and profiles through CDP
    Crash symbolicationApple crash artifacts only (.ips, .crash, or log style), symbolicated against local .dSYM bundles with atos. Android Java and R8 mapping, and native ndk-stack output, are out of scope.Crash symbolication
    Native profiles and tracesUse perf cpu profile for Apple xctrace or Android simpleperf profiles, and perf trace for supported Apple xctrace or Android Perfetto captures; both need a supported app session. The separate trace command captures session diagnostic logs.Native profiles and traces
    .ad replay scripts and the replay test runnerRuns supported .ad actions subject to target support and replay restrictions. Some resource operations are unavailable inside bounded replay even when they work standalone..ad replay scripts and the replay test runner
    Batched command runsRuns registry-approved batch commands serially in one session. Target admission still applies, and lifecycle and resource restrictions can reject operations that work standalone.Batched command runs
    Maestro flow import and .ad exportRuns a documented subset of Maestro YAML on iOS and Android only. Exports compatible .ad actions to Maestro YAML; unsupported actions and selector shapes fail with source context, and semantic differences produce warnings.Maestro flow import and .ad export
    MCP serverOne agent-device mcp server per daemon exposes the device commands that mark themselves MCP-exposed, including provider sessions already connected on that daemon.MCP server
    Typed Node.js APIThe typed client exposes device and session operations through domain methods and client.command. Daemon-backed methods share CLI command semantics and target restrictions; the client does not expose every CLI entry point.Typed Node.js API
    Named sessions, leases, and parallel runsSessions and leases are daemon state, so parallel runs come from separate session names, device allowlists, and worktrees rather than from the target. Two worktrees can drive two platforms from one checkout.Named sessions, leases, and parallel runs
    Remote daemon and device hostA proxy between the agent machine and the device host forwards the same daemon surface, so the device rows above apply across it. Provider clouds need no proxy.Remote daemon and device host
    Hosted device providersBrowserStack, AWS Device Farm, TestMu AI, and Limrun appear as their own columns above. Provider artifact lookup after close works for the three WebDriver providers; Limrun keeps no artifacts.Hosted device providers
    Native, React Native, Expo, and Flutter appsNative and Flutter apps use the interactions and accessibility data exposed by their target. React Native and Expo development builds can additionally expose React component inspection, render profiling, and Metro CDP tools when their documented prerequisites are met.Native, React Native, Expo, and Flutter apps
